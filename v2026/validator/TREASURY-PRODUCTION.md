# Native treasury production successor

The treasury successor uses the existing schema-3 production config and V2 measured, prepared, submitted and recovery path. Select `treasury_approval` instead of `owner_recycle_approval`; the two selectors cannot coexist. The approval, proposal, production scope, decision proof, signature and native source commitment have explicit treasury domains. Omitted treasury fields preserve the original owner-recycle wire bytes and hashes.

The selected `ur-reserve` launch only receives funds. Its supplied native destination is AccountId32 `0x1815103f41a8d1e24c55d380c6f843fb36d715b4322a4e4f02bff36dfe74a410` (SS58 `5CcHGEqKK3RXeEA2sVycHQAQGrqsyhWaYu9FjGtDVN6nwMwR`). Receive-only admission requires no multisig reconstruction, signatory identities, device configuration or general reserve signing/spending qualification. An EVM wallet address cannot substitute for the native account.

`TreasuryPolicy` selects the explicit receive-only schema `urnetwork-native-treasury-receive-policy-v1` (`TreasuryReceivePolicySchema`). Its existing `MultisigAccount` carrier, serialized as `multisig_account`, contains the supplied public native receiver for compatibility; that field name asserts no multisig signing authority in this schema. Threshold is zero and signatories are null. The complete recipient roster binds each actual UID, hotkey and registration block. The policy fixes provider share `1/10`, treasury share `9/10`, cap `32768/65535`, and an optional exact auto-stake destination. A nil destination requires the native storage entry to be absent.

The separate public descriptor is `urnetwork-native-treasury-destination-v1`, with `profile: mainnet`, `netuid: 25`, `genesis_hash`, `account_id` and `recipient_hotkeys` as canonical AccountId32 strings. The [mainnet destination commands](../mainnet/TREASURY-EMISSIONS.md#public-configuration-contract) use `--destination FILE --destination-sha256 HASH` for `describe`, `observe` and `policy-plan`. Describe can accept an empty list to record the known destination. Policy planning requires the full authenticated registered roster and produces unsigned `approved: false` output; independent signed policy approval remains required. If `vault/main/sn.yml` contains root keys or other private fields, these commands require a separate public-only snapshot. Never give them the combined vault file or insert the descriptor into the strict `config/main/sn.yml` earnings schedule.

Admission authenticates the original metadata and storage at one pinned canonical finalized block. Each of at least two recipients must remain an ordinary registered hotkey whose actual `Owner` is the approved native receiver. The account must differ from `SubnetOwner`. All registered `OwnedHotkeys[SubnetOwner]` and the explicit `SubnetOwnerHotkey` are excluded. `OwnerHotkeys` in the shared signed carrier records that exact exclusion census, not treasury recipients. Changed ownership, UID, generation, masks or destination refuses the complete row. An address alone does not establish this roster. Missing recipients require one-time external registration and fresh authenticated readback before routing; no policy may fabricate ownership or generations.

The validator itself may run on the subnet owner hotkey. That exclusion census then contains the validator, which the treasury row never weights. Admission accepts this owner-validator form only for the approval's own `validator_hotkey`, and only when the census reads it as the explicit `SubnetOwnerHotkey` whose `Owner` is `SubnetOwner`. Another owned hotkey cannot take this form, and neither can a foreign one. No other approved validator may be an owner. Owner-recycle approvals weight their owner census, so their validator can never be in it. Production eligibility does not accept the runtime's subnet-owner submission exception for an owner-validator: it must still hold a validator permit and the threshold stake.

The original `urnetwork-native-treasury-policy-v1` schema remains a separate strict multisig mode. Its threshold, canonical sorted signatories and `crv4.DeriveNativeMultisigAccount` derivation checks and original hashes remain unchanged. The earlier confirmed 2-of-3 custody information applies only if that optional sending workflow is selected, with its actual complete signer set and qualified hardware. Receive-only policy cannot supply spending authority or replace the strict `--custody` descriptor. Validators receive no treasury private keys, seeds, device paths or signer references. Receiving native incentive requires no reserve or recipient signature; hardware operations remain separate from these observers.

The original provider artifact supplies all provider scores and complete validator masks. With two approved treasury recipients the exact unquantized row assigns 45% to each and 10% to providers. Only for an exclusive treasury selection in a mainnet schema-3 config, when the replayed provider allocation is genuinely empty (no positive unmasked pool or head weight), the row is reserve-only instead: each approved recipient takes 1/n of the whole row (1/2 each with two) and providers nothing. The measured row then carries `fallback: reserve_only_empty_provider_allocation`, and every verifier rederives the empty allocation from the provider measurement before accepting it; any remaining provider weight refuses the fallback. Owner-recycle, testnet and the preview planner keep their refusal of an empty allocation. Existing quantization, cap and minimum-weight checks still apply; a missing or masked treasury recipient never causes redistribution. Theta remains inside the provider component. A prepared row is not evidence of the final native miner allocation or spendable credit. Independent execution observations must check the then-current owner exclusions, collateral, auto-stake destination and native conservation.

The exported tooling entry points are `ObserveTreasuryAdmission`, `ObserveTreasuryAdmissionAt`, `ObserveTreasuryMeasurementAuthority`, `SealTreasuryMeasurement`, `ReplayTreasuryMeasurement`, `RetainTreasuryApproval` and `BuildTreasuryProductionAuthority`. `DecodeTreasuryApproval` verifies a complete production config. `VerifyTreasuryApproval` and `VerifyTreasuryApprovalPolicy` verify the exact canonical approval bytes against an independently pinned signer and content hash for native accounting consumers; consumers must additionally join the returned signed genesis, netuid, runtime/source, policy and finite activation scope to their execution. These projection APIs grant neither prepared-transaction authority nor signing custody.

An owner-to-treasury transition requires an independently signed advancing policy and drained activation epoch. The previous owner intent must be applied. Historical authority bundles retain the exact original config and approval as read-only authority. Restart, archive intent replay and native source capture select that original authority by its signed sidecar, including the original first epoch and activation metadata. Historical startup anchors at the oldest retained authenticated activation, so an unrelated current metadata outage cannot strand an old liability. Current preparation still requires current authority.

The authored treasury regressions cover actual measured preparation, raw native custody drift, masks and roster refusal, approval and sidecar substitution, submission/restart recovery, original wire compatibility, owner-to-treasury transition, bounded read causes, storage shape, and distinct original activation/decision/successor capture. Source formatting and independent source review are separate from compiler, normal/race body and mutation-control qualification; those executions belong to the designated execution owner.
